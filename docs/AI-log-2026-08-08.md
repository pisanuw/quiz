## Session: focus ring bug

Reported: a box appeared around the answer slot you picked on the previous
question. Cause was `key={i}` on the choice list. Same list length and shape
every question, so React reused the button nodes, the clicked one held focus,
and `*:focus-visible` in index.css drew the outline. State was correct
throughout; only the ring was stale.

Fix: key the question block by question id so it remounts, key choices by
question id plus index, and move focus to the prompt heading (tabIndex -1,
outline suppressed since the focus move is programmatic).

Verified by build only. No browser test was run in this environment.

## Session: attempt counts

Requested: track how many times each person takes a quiz and show it in
parentheses next to their score on the leaderboard.

No schema change needed. `attempts` already stored every submission, only the
best was being surfaced. Both leaderboard views were dropped and recreated
(`20260809012217_attempt_counts`) with an `attempts` column: a grouped count
joined to the existing distinct-on subquery, which leaves the best-score and
earliest-achievement tiebreak semantics untouched. `leaderboard_global` sums
attempts across chapters. Counts are retroactive.

First session where the SQL was actually executed rather than eyeballed.
Installed Postgres 16 locally, shimmed `auth.users` and `auth.uid()`, replicated
Supabase's default grants on the public schema, and ran all migrations in order.
Verified with two test players: attempt counts increment through
`submit_attempt()`, a later tie on best score still loses to the earlier one,
anon is refused grading, anon sees zero questions, authenticated sees zero
answer keys.

That last check surfaced something. `answer_keys` was protected by RLS alone,
while Supabase's default privileges still grant client roles SELECT on it. RLS
with no policies returns zero rows, so it was safe, but only one layer deep.
Added `20260809012222_lock_answer_keys` to revoke the grant outright. Verified
that grading still works afterwards, since submit_attempt() is security definer.

## Session: leaderboard 400 and migration reconciliation

Site returned "column leaderboard_global.attempts does not exist". Cause was
mine: the client change and the migration went out in one commit, Netlify
builds on push, the database does not. PostgREST rejects an unknown column in
the select list outright, so the `?? 0` fallback in the component could not
absorb it. Future schema-dependent changes go out as two commits, migration
first.

Applied `attempt_counts` and `lock_answer_keys` through the Supabase connector
after checking that nothing outside the two views depended on them. Verified
the column exists, both views return rows, answer_keys is now unreadable by
anon and authenticated, and the board is still public.

Then reconciled migration history. Two mismatches, not one:

1. `init` had never been recorded at all, so it was applied through the SQL
   editor rather than a tracked route. Inserted version 20260808120000.
2. Three files were named with timestamps I invented, while the database had
   recorded the real application times. Renamed the files to match the
   database, since the database is the record of what actually ran:
   require_signin to 20260808234321, attempt_counts to 20260809012217,
   lock_answer_keys to 20260809012222.

Discovered while doing this: the quiz has no Supabase project of its own. It
shares `upvoteme` with upvoteme, word-path, and a tutoring system, and
therefore shares one migration history. `supabase db push` is not usable from
this repo because remote history contains migrations with no local file.
Documented in README under "Shared database", including which objects belong
to this app, since `public` holds another table called `leaderboard` that does
not.
