## Session: focus ring bug

Reported: a box appeared around the answer slot you picked on the previous
question. Cause was `key={i}` on the choice list. Same list length and shape
every question, so React reused the button nodes, the clicked one held focus,
and `*:focus-visible` in index.css drew the outline. State was correct
throughout; only the ring was stale.

Fix: key the question block by question id so it remounts, key choices by
question id plus index, and move focus to the prompt heading (tabIndex -1,
outline suppressed since the focus move is programmatic).

Verified by build only. No browser test was run in this environment.

## Session: attempt counts

Requested: track how many times each person takes a quiz and show it in
parentheses next to their score on the leaderboard.

No schema change needed. `attempts` already stored every submission, only the
best was being surfaced. Both leaderboard views were dropped and recreated
(`20260809012217_attempt_counts`) with an `attempts` column: a grouped count
joined to the existing distinct-on subquery, which leaves the best-score and
earliest-achievement tiebreak semantics untouched. `leaderboard_global` sums
attempts across chapters. Counts are retroactive.

First session where the SQL was actually executed rather than eyeballed.
Installed Postgres 16 locally, shimmed `auth.users` and `auth.uid()`, replicated
Supabase's default grants on the public schema, and ran all migrations in order.
Verified with two test players: attempt counts increment through
`submit_attempt()`, a later tie on best score still loses to the earlier one,
anon is refused grading, anon sees zero questions, authenticated sees zero
answer keys.

That last check surfaced something. `answer_keys` was protected by RLS alone,
while Supabase's default privileges still grant client roles SELECT on it. RLS
with no policies returns zero rows, so it was safe, but only one layer deep.
Added `20260809012222_lock_answer_keys` to revoke the grant outright. Verified
that grading still works afterwards, since submit_attempt() is security definer.

## Session: leaderboard 400 and migration reconciliation

Site returned "column leaderboard_global.attempts does not exist". Cause was
mine: the client change and the migration went out in one commit, Netlify
builds on push, the database does not. PostgREST rejects an unknown column in
the select list outright, so the `?? 0` fallback in the component could not
absorb it. Future schema-dependent changes go out as two commits, migration
first.

Applied `attempt_counts` and `lock_answer_keys` through the Supabase connector
after checking that nothing outside the two views depended on them. Verified
the column exists, both views return rows, answer_keys is now unreadable by
anon and authenticated, and the board is still public.

Then reconciled migration history. Two mismatches, not one:

1. `init` had never been recorded at all, so it was applied through the SQL
   editor rather than a tracked route. Inserted version 20260808120000.
2. Three files were named with timestamps I invented, while the database had
   recorded the real application times. Renamed the files to match the
   database, since the database is the record of what actually ran:
   require_signin to 20260808234321, attempt_counts to 20260809012217,
   lock_answer_keys to 20260809012222.

Discovered while doing this: the quiz has no Supabase project of its own. It
shares `upvoteme` with upvoteme, word-path, and a tutoring system, and
therefore shares one migration history. `supabase db push` is not usable from
this repo because remote history contains migrations with no local file.
Documented in README under "Shared database", including which objects belong
to this app, since `public` holds another table called `leaderboard` that does
not.

## Session: board 400 again, and scoring model drift

Same error text as before but a different cause, which is why I reproduced it
through the REST API with the anon key instead of trusting a psql check. The
per-chapter board returned 200 with attempts present; only the global board
returned 400. That ruled out a stale PostgREST cache.

Cause: a migration named leaderboard_average (version 20260809231511) was
applied directly to the database and never committed. It recreated both views
to average scores across attempts instead of taking the best, and in doing so
dropped attempts from leaderboard_global while the deployed client still
selected it.

Fix: recreated leaderboard_global with attempts restored, preserving the
averaging semantics exactly. Did not revert the scoring change, which looks
deliberate and is a product decision, not mine to reverse. Verified all four
client queries return 200 against the live REST endpoint.

Captured both migrations as repo files. The averaging one is marked
RECONSTRUCTED in its header because it was rebuilt from pg_get_viewdef() and is
not the original text.

Flagged separately: averaging contradicts the documented rules, makes the
attempts count actively misleading, leaves leaderboard_quiz.best_score holding
something that is not a best score, and changes the global board from a sum to
an average of averages. Left for a decision rather than patched.

## Session: global board as a sum, and the alias drop

Scoring confirmed as the mean of attempts. Global board changed from mean of
chapter means to sum of chapter means out of a computed max_score, because the
mean version penalised breadth: ten chapters at 17.0 lost to one at 18.0.
Renamed leaderboard_quiz.best_score to avg_score. total_score kept its name,
since under a sum it is accurate again, which is a departure from the literal
instruction and was flagged.

Two-phase deploy, in response to having broken the site twice by changing the
database and client together. Phase one shipped the new views with best_score
retained as a duplicate of avg_score, so both the old and new bundles worked.
Verified both query shapes returned 200 before pushing the client.

Phase two dropped the alias, but only after fetching the deployed bundle from
Netlify and confirming it requests avg_score and contains no occurrence of
best_score. Comparing asset hashes would not have worked, since Netlify inlines
the Supabase env vars and the local build does not.

The drop needed a correction. create or replace view cannot remove a column, so
the staged file was invalid and Postgres rejected it. Rewrote as drop and
recreate for both views, since leaderboard_global depends on leaderboard_quiz,
tested locally, then applied. Verified afterwards that all four client queries
return 200 and that selecting best_score now returns 400.

## Session: initials, photo opt in, account menu

Requested: initials as the default leaderboard identity with no picture, an
option to change display name and to switch the Google photo on, and a nav
where the avatar opens a menu containing sign out, with sign in shown only when
signed out.

Built the identity part in SQL rather than the client, because hiding a photo
in the interface while still sending its URL over the API is not hiding it.
profiles gained full_name and show_avatar; handle_new_user now stores initials
as display_name and keeps the Google name separately; leaderboard_quiz emits
avatar_url only when show_avatar is set. Existing rows were backfilled, and
display_name was reset to initials only where it still equalled the Google
name, so a player who had already chosen a name would keep it. Both live
profiles became YP and JM.

Column level grants restrict players to updating display_name and show_avatar,
so avatar_url cannot be pointed at an arbitrary image.

Then found a real hole while verifying through the REST API: public.profiles
still carried a readable-by-everyone policy, so the raw avatar_url of every
player, including opted-out ones, could be selected straight off the table. The
view gating was decorative. Replaced the policy with owner-only reads; the
leaderboard views are unaffected since they bypass RLS as owner-owned views.
Confirmed a stranger now gets an empty array from profiles while the board
still renders.

Nav rebuilt: the You link is gone, the avatar is a menu trigger with
aria-haspopup and aria-expanded, and the menu closes on outside pointerdown, on
Escape, and on route change.
