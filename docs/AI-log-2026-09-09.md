# AI log, 2026-09-09

## Session: leaderboard views to security definer functions

Supabase's advisor flagged `public.leaderboard_global` as a Security Definer
View. Both boards are owned by postgres with `security_invoker` off, so they
read past row level security. That bypass is intentional and load bearing:
`attempts` is own-rows-only and `profiles` became own-row-only in
20260812191841, so the views are the only way anyone sees another player. So
flipping `security_invoker` on would not fix it, it would empty both boards.

The fix follows the rule already in CLAUDE.md: a read path over RLS goes through
a security definer function, like `submit_attempt()`. Replaced both views with
`leaderboard_quiz()` and `leaderboard_global()`, same column shapes and types
byte for byte, execute revoked from public and granted to anon and
authenticated. Functions do not trip the view advisor, so the finding clears
once the views are gone.

Shipped as two migrations, not one, because dropping the views in lockstep with
a client that still selects them is the exact DB-ahead-of-client skew that
returned a 400 board three times before. A function and a view can share a name
(`pg_proc` vs `pg_class`) and PostgREST routes `/rpc/leaderboard_global` and
`/leaderboard_global` separately, so phase one (20260909130713) adds the
functions while the views stay, both clients work. Phase two (20260909131044)
drops the views, applied only after the rpc client is live. The client changes
from `.from(view)` to `.rpc(fn)` in three functions in `src/lib/api.js`;
PostgREST still applies select, eq, order and limit to a set returning
function, so the queries read the same.

Verified against a throwaway Postgres 16 with the auth shims: all twelve
migrations apply in order, and as anon both functions aggregate across two
seeded players with matching scores, ranks and max_score, while a direct select
on attempts and on profiles returns zero rows. The views are gone afterwards.
Then applied phase one to the live upvoteme project (ref arktxlrlyceffyozdwhq,
the shared prod database) through the connector. The connector recorded it as
version 20260909130713, so the two local files were renamed to match the
database, keeping the earlier convention that the database is the record of what
ran. Verified on live data that the function and the view return identical rows
(YP 52.7 over three chapters, JM 12.0), so the deployed view client is
unaffected and the rpc client is now safe to deploy. Client build passes after
npm install populated the missing vite and plugin.

Completed the rollout in the same session. After Netlify built the push, fetched
the deployed bundle (index-CTYoAVFt.js) and confirmed it calls rpc for both
boards with no from() left on the views, so no client path still needed them.
Applied phase two 20260909131044 to drop both views. Verified on prod: zero
leaderboard views remain, both functions present and returning rows, and the
Security Definer View advisory is gone.

The fix trades that finding for the expected one. The two functions now appear
under the SECURITY DEFINER function executable by anon and authenticated
advisories (lints 0028 and 0029), next to submit_attempt which already carried
them. That is intentional and unavoidable for a public board: any anon callable
path that aggregates across RLS-protected rows trips one advisory or the other,
and the function is the explicit, reviewable form the schema already
standardises on. Acknowledge those, do not switch to invoker, which would empty
the board.
